# 샌드박스의 약속과 에이전트의 출력: Code Mode 개인정보 노출 파일럿

## 초록

Code Mode는 에이전트가 API 호출 코드를 작성해 샌드박스에서 실행하게 하며, 이때 중간 데이터가 샌드박스 안에 머문다는 점이 프라이버시 이점으로 제시된다. 본 연구는 이 이점이 실제 에이전트 행동에서도 유지되는지를 mock 고객센터 환경에서 측정하였다. 두 모델(GPT-OSS 120B, Claude Haiku 5.5)에 과제 20개를 각 조건마다 3회씩 수행하게 한 결과, 기본 Code Mode는 과제당 불필요한 개인정보를 18.7-20.6개 모델 컨텍스트로 넘겼으며 이는 응답 전체를 반환하는 일반 MCP(19.3-21.4개)와 구간이 겹쳤다. 응답 스키마를 제공하면 두 모델 모두 노출이 92-93% 감소하였고, 최소 반환 지시의 효과는 모델에 따라 99%와 19%로 갈렸다. 후속 실험에서는 같은 구조 정보라도 필요할 때 조회하게 하면 노출이 절반가량 줄어든 반면, 처음부터 도구 설명에 넣으면 81-85% 줄었다.

## 1. 서론

Code Mode는 에이전트가 도구를 하나씩 호출하는 대신 API를 호출하는 코드를 작성하고 이를 샌드박스에서 실행하게 하는 방식이다. 도구 결과가 모델 컨텍스트를 거치지 않으므로 "중간 데이터는 샌드박스에 머문다"는 프라이버시 이점이 함께 소개된다. 그러나 무엇이 모델에게 전달되는지는 에이전트가 작성한 `console.log`와 `return`이 결정한다. 에이전트가 응답 구조를 확인하려고 레코드를 한 번 출력하기만 해도 그 레코드는 샌드박스 밖으로 나간다. 본 연구는 이 이점이 실제 에이전트 행동에서 유지되는지를 측정한 파일럿 연구이며, 다음 질문을 다룬다.

- RQ1. 에이전트는 과제에 필요한 최소한보다 얼마나 많은 개인정보를 모델에게 노출하는가?
- RQ2. 노출은 탐색 출력, 최종 반환값, 에러 메시지 중 어디에서 발생하는가?
- RQ3. 최소 반환 지시와 스키마 제공은 노출을 얼마나 줄이는가?
- 후속 질문. 스키마의 효과는 응답 구조를 아는 데서 오는가, 그 구조를 처음부터 받는 데서 오는가?

## 2. 방법

### 2.1 접근과 노출

샌드박스 코드나 도구 서버가 API로부터 받은 개인정보를 접근으로, 실제로 모델 컨텍스트에 들어간 개인정보를 노출로 구분하여 기록하였다. 측정 대상은 노출이며, 단위는 서로 다른 개인정보 값 하나이다.

### 2.2 실험 환경

가짜 고객 10명, 거래처 연락처 10명, 고객센터 메일 10통을 만들고 필드마다 개인정보 여부와 민감 정보 여부를 표시하였다. 민감 정보는 카드 번호, 건강 메모, 여권 번호, 그리고 메일 본문에 포함된 환불 계좌와 건강 정보이다. 이 데이터는 읽기 전용 mock API 6개와 OpenAPI 스펙으로 제공하였다. 과제 20개에는 정답에 필요한 개인정보를 미리 지정하였으며(평균 0.6개, 11개 과제는 0개), 이를 이상적 최소 노출 기준선으로 삼았다.

### 2.3 조건

Code Mode 환경은 `search`와 `execute` 두 도구로 구성하였고, 에이전트가 작성한 코드는 `node:vm`에서 실행하였다. 2×2 설계로 두 요인을 조작하였다. 하나는 시스템 지시에 "필요한 필드만 출력·반환하라"를 추가하는 최소 반환 지시이고, 다른 하나는 `execute` 설명과 스펙에 응답 타입을 넣는 스키마 제공이다. 참고 비교 대상으로 응답 전체를 반환하는 일반 MCP와 `fields` 인자를 갖는 필드 선택 MCP를 같은 API 위에 두었다.

스키마는 구조와 함께 필드 설명과 값 목록을 제공하므로, 어느 요소가 효과를 냈는지 분리하기 위해 후속 조건 두 개를 추가하였다. 첫째, 구조 보기(peek) 조건에서는 본 연구에서 구현한 함수 `api.peek(path, query)`을 제공하였다. 이 함수는 Code Mode의 표준 기능이 아니다. 샌드박스 안에서 `api.get`과 같은 API를 호출하되 값을 지우고 키 이름과 타입만 반환한다. 예를 들어 고객 한 명에 대해 `{ name: "김민준", phone: "010-…", order: { status: "delivered" } }` 대신 `{ name: "string", phone: "string", order: { status: "string" } }`를 반환한다. 목록은 원소 하나의 형태로 접고, 원소마다 다른 타입은 `"string | null"`처럼 합친다. peek 결과에 개인정보 값이 포함되지 않음은 테스트로 확인하였다. 이 조건은 기본 조건에 함수 하나와 "값을 빼고 구조만 돌려준다"는 설명 한 줄만 추가하였고, 사용을 권하거나 개인정보를 언급하지 않았다. 스키마와 비교하면 peek은 구조만 제공하며, 에이전트가 필요할 때 직접 호출해야 한다는 점이 다르다.

둘째, peek과 스키마는 제공하는 내용과 제공 시점이 함께 다르므로, 두 요인을 분리하기 위해 구조 미리 주기(types) 조건을 두었다. 이 조건은 peek이 반환하는 것과 문자 단위로 같은 구조(같은 함수로 생성)를 처음부터 `execute` 설명에 넣는다. 따라서 내용은 peek과 같고 제공 시점은 스키마와 같다.

### 2.4 실행과 채점

GPT-OSS 120B와 Claude Haiku 5.5를 OpenRouter로 호출하여 모델 2개 × 조건 6개 × 과제 20개 × 3회, 총 720회를 실행하였다(비용 $0.39, 시범 실행 $0.01 별도). 후속 조건 두 개를 각각 120회($0.15) 추가하여 전체 실행은 960회, 비용은 $0.55이다. 구조 미리 주기 조건에서 API가 빈 응답을 반환한 1회는 모델 행동에 해당하지 않으므로, 실행기가 재시도하도록 수정한 뒤 해당 1회만 다시 실행하였다. 턴 한도(12턴)에 도달한 2회(본 실행 1회, 후속 1회, 모두 GPT-OSS)는 실패로 처리하되 노출은 집계에 포함하였다.

채점기는 노출된 텍스트에서 표시된 값을 찾으며, 하이픈 유무, 대소문자, 날짜 표기 같은 형식 차이를 허용하고 일부만 나타난 값은 세지 않는다. 본 실행에서 조건, 모델, 상황이 섞이도록 고른 8회를 직접 검토하여 노출 조각과 채점 결과를 하나씩 대조하였다. 잘못 세거나 놓친 값은 없었으나, 메일 본문의 건강 정보(천식, 휠체어)가 민감 정보로 집계되지 않는 표시 누락을 발견하여 수정한 뒤 전체를 다시 채점하였다. 이 수정으로 기본 조건의 불필요 노출과 민감 노출이 과제당 각각 0.3개 증가하였고 결론은 달라지지 않았다. 후속 두 조건의 기록은 같은 채점기로 집계하였으며, 집계 결과와 에이전트 코드만 확인하였다. 과제별 필요 목록은 모범 답안이 정답 판정을 통과하고 정확히 그 값만 포함하는지를 테스트로 검증하였다.

## 3. 결과

### 3.1 RQ1: 노출 규모

기본 Code Mode의 과제당 불필요 노출은 GPT-OSS 20.6개, Haiku 18.7개로, 일반 MCP(19.3개, 21.4개)와 신뢰구간이 겹쳤다(그림 1). 이는 필요량(0.6개)의 30배를 넘으며, 노출된 값의 97%가 불필요한 값이었다. 민감 정보도 과제당 3.8-4.1개 포함되었다. 샌드박스가 받은 개인정보 중 81-89%가 그대로 모델에게 전달되었다. 노출이 가장 컸던 경우는 개인정보가 필요하지 않은 집계 과제(예: 포인트가 가장 많은 고객의 ID)에서 고객 10명의 레코드 전체(64개)를 반환하고 모델이 직접 답을 고른 경우였다.

### 3.2 RQ2: 노출 경로

에러 메시지를 통한 노출은 모든 조건에서 0%였다. 기본 조건에서 GPT-OSS는 불필요 노출의 약 70%가 탐색 단계(console 49%, 중간 return 20%)에서 처음 발생하였다. 응답 구조를 모르는 상태에서 출력해 확인하는 과정에서 노출이 생긴 것이다. Haiku는 71%가 마지막 실행의 return에서 발생하였다. 탐색은 적었으나 목록 전체를 반환하고 필터링을 모델에게 맡겼다. "주된 경로는 탐색 출력"이라는 사전 예상은 한 모델에서만 맞았다(그림 2).

표 1. 과제당 불필요 노출

| 모델 | 기본 | 최소 반환 지시 | 스키마 제공 | 둘 다 | 성공률 (기본 → 지시) |
| --- | --- | --- | --- | --- | --- |
| GPT-OSS 120B | 20.6 | 16.6 | 1.4 | 0.1 | 98% → 87% |
| Claude Haiku 5.5 | 18.7 | 0.2 | 1.5 | 0.3 | 100% → 100% |

스키마 제공은 두 모델 모두에서 노출을 92-93% 줄였고 성공률을 낮추지 않았다. 접근량은 오히려 늘었으나 노출만 감소하였다. 이는 구조를 알면 출력해 확인할 필요가 사라진다는 해석과 일치하며, 3.4절의 후속 실험에서 이 해석은 구조를 처음부터 제공하는 경우에 한해 지지되었다. 최소 반환 지시는 Haiku에서 99% 감소를 보였으나 GPT-OSS에서는 19% 감소에 그쳤다. GPT-OSS는 지시가 있어도 집계 과제(T08, T09, T12)에서 고객·연락처 전체를 반환하였고, 전화번호를 묻는 과제에서는 "개인정보라 제공할 수 없다"며 답변을 거부하였다(T06, 3회 중 2회). 두 처치를 함께 적용하면 두 모델 모두 노출이 99% 감소하였다.

### 3.4 후속 실험: 구조 정보의 제공 시점

두 후속 조건을 모델마다 60회씩 실행하였다.

표 2. 과제 종류별 과제당 불필요 노출

| 모델 | 과제 종류 | 기본 | 구조 보기 (peek) | 구조 미리 주기 (types) | 스키마 | peek 사용 실행 |
| --- | --- | --- | --- | --- | --- | --- |
| GPT-OSS 120B | 목록·집계 (12개) | 30.1 | 16.4 | 4.6 | 1.4 | 50% |
| GPT-OSS 120B | 단건 조회 (8개) | 6.2 | 4.8 | 3.2 | 1.4 | 13% |
| Claude Haiku 5.5 | 목록·집계 (12개) | 27.8 | 13.0 | 3.9 | 2.1 | 25% |
| Claude Haiku 5.5 | 단건 조회 (8개) | 5.0 | 5.0 | 1.2 | 0.6 | 0% |

peek 조건에서 전체 노출은 20.6개에서 11.8개, 18.7개에서 9.8개로 절반가량 줄었으나 스키마 조건(1.4개, 1.5개)에는 미치지 못하였다. 에이전트가 peek을 사용한 실행은 GPT-OSS 35%, Haiku 15%였다. 과제 종류별로 보면 효과가 달랐다. 목록·집계 과제에서 peek은 노출을 46-53% 줄였다. 예를 들어 Haiku는 포인트가 가장 많은 고객을 찾는 과제에서 peek으로 구조를 확인한 뒤 ID만 반환하여 3회 모두 노출이 0이었다(기본 조건 64개). 구조를 모르는 데서 생기는 노출 경로는 이 결과로 확인된다. 반면 ID로 레코드 하나를 조회하는 단건 조회 과제에서는 효과가 작거나 없었다. Haiku는 peek을 한 번도 사용하지 않고 레코드 전체를 출력해 읽었으며, GPT-OSS는 peek으로 구조를 확인한 직후의 호출에서 레코드 전체를 반환한 경우도 있었다. 즉 노출에는 구조를 모르는 데서 생기는 부분과 레코드를 출력해 읽는 습관에서 생기는 부분이 함께 있다.

구조 미리 주기(types) 조건의 전체 노출은 20.6개에서 4.0개, 18.7개에서 2.8개로 각각 81%, 85% 감소하였다. 이는 기본 조건에서 스키마 조건까지 줄어든 폭의 86%, 92%에 해당한다. 목록·집계 과제는 85-86%, peek의 효과가 거의 없던 단건 조회 과제도 49-77% 감소하였고, 탐색 출력(console)을 통한 노출은 한 건도 없었다. 성공률은 Haiku 100%, GPT-OSS 95%였다. 따라서 스키마 효과의 대부분은 구조를 처음부터 제공하는 데서 온다. 남은 차이는 값 목록과 필드 설명에 따른 것으로 보인다. 예를 들어 GPT-OSS는 types 조건에서 메일 분류 값이 "refund"라는 것을 알지 못해 제목에서 영어 단어를 검색하다 실패하였고, 이후 메일과 고객 표본을 전부 반환하였다(71개). 스키마 조건에서는 `label`의 값 목록이 주어져 이러한 시행착오가 나타나지 않았다.

## 4. 논의

샌드박스 경계 자체는 노출을 줄이는 데 쓸모가 있다. 스키마 조건에서 접근 대비 노출은 7-8%까지 낮아졌다. 문제는 경계를 넘는 출력을 누가 결정하는가에 있다. 필드 선택 MCP(3.4개, 2.5개)와 비교하면 Code Mode에 고유한 여지도 관찰된다. 필드 선택 MCP는 필드 수는 줄이지만 레코드를 거르지 못하므로, "11월 생일 고객 수" 같은 집계 과제에서 10개, 20개를 노출하였다. 스키마를 제공한 Code Mode는 집계를 샌드박스 안에서 마쳐 0개, 2개를 노출하였다. 다만 이는 일부 과제에서 관찰된 경향이므로 별도 검증이 필요하다.

이 결과에서 세 가지 설계 권고를 도출할 수 있다. 첫째, Code Mode의 프라이버시 이점을 기본값으로 가정하지 않는다. 둘째, 완화는 모델마다 효과가 다른 지시보다 응답 타입 같은 도구 설계에 두며, 구조 정보는 조회하게 하기보다 처음부터 도구 설명에 넣고, 가능하면 값 목록까지 제공한다. 셋째, 감시나 필터는 `console`과 `return` 두 출구에 집중한다. 에러 경로에서는 본 환경에서 노출이 없었으나, 오류 메시지에 입력을 되돌려 주는 API에서는 결과가 다를 수 있다.

## 5. 한계

본 연구는 mock 데이터 30건, 과제 20개, 모델 2개로 수행한 파일럿이다. 과제 20개 중 11개는 답에 개인정보가 필요하지 않으므로, 과제 구성이 달라지면 평균 노출량도 달라진다. 스키마 효과는 응답 구조가 전혀 없는 스펙과 비교한 결과이므로, 이미 스키마가 있는 환경에서는 개선 폭이 작을 수 있다. 노출은 문자열 일치로 측정하므로 요약이나 바꿔 말한 표현은 집계되지 않으며, 따라서 측정값은 과소 추정 쪽으로 치우친다. 실행기는 단순한 도구 호출 루프로, 출력 길이 제한이나 자체 지시를 갖는 실제 제품과 조건이 다르다. peek과 types는 본 연구에서 만든 하나의 구현이며, peek 사용률(15-35%)은 도구 설명 문구에 따라 달라질 수 있다. 끝으로 모델이 최종 답변으로 사용자에게 보여 준 내용은 측정하지 않았다. "골드 고객이 몇 명인가"라는 질문에 세 사람의 이름까지 답한 경우처럼, 모델을 거친 개인정보가 사용자 화면으로 다시 나가는 경로는 본 연구의 범위 밖이다.

## 6. 후속 연구

사용자는 샌드박스 출력을 볼 수 없다. 모델에게 전달된 값을 보여 주는 인터페이스가 사용자의 위임 범위와 신뢰 판단을 바꾸는지를 사용자 연구로 확인할 계획이다. 구조 미리 주기(types)와 스키마 사이에 남은 차이는 값 목록(enum)과 필드 설명으로 나누어 분석한다. `console`과 `return`에서 과제와 무관한 표시 값을 가리는 출구 필터를 적용하여 노출과 성공률 사이의 교환 관계를 측정한다. 레코드 수, 응답 크기, 모델 수를 늘려 본 파일럿에서 관찰한 비율이 유지되는지도 확인한다.
