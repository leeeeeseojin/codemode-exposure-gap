# 샌드박스의 약속과 에이전트의 출력: Code Mode 개인정보 노출 파일럿

## 1. 동기

Code Mode는 에이전트가 API를 부르는 코드를 짜서 샌드박스에서 실행하게 한다. 도구 결과가 모델 컨텍스트를 거치지 않으므로
"중간 데이터는 샌드박스에 머문다"는 프라이버시 이점이 함께 소개된다. 그러나 모델에게 무엇이 넘어갈지는 에이전트가 쓴
`console.log`와 `return`이 정한다. 응답 구조를 확인하려고 레코드를 한 번 찍기만 해도 그 레코드는 경계 밖으로 나간다.
이 파일럿은 그 약속이 실제 에이전트 행동에서 지켜지는지를 잰다.

- RQ1. 과제에 필요한 최소한보다 얼마나 많은 개인정보를 모델에게 노출하는가?
- RQ2. 노출은 탐색 출력, 최종 반환값, 에러 메시지 중 어디서 생기는가?
- RQ3. 최소 반환 지시와 스키마 제공은 노출을 얼마나 줄이는가?
- 후속. 스키마의 효과는 무엇에서 오는가? 구조를 아는 것인가, 그 구조를 처음부터 받는 것인가?

## 2. 방법

**접근과 노출.** 샌드박스 코드나 도구 서버가 API에서 받은 개인정보를 *접근*, 실제로 모델 컨텍스트에 들어간 것을 *노출*로 나눠 기록했다.
측정 대상은 노출이고, 단위는 서로 다른 개인정보 값 하나다.

**환경.** 가짜 고객 10명, 거래처 연락처 10명, 고객센터 메일 10통을 만들고 필드마다 개인정보·민감 정보 라벨을 붙였다.
민감 정보는 카드 번호, 건강 메모, 여권 번호, 메일 본문 속 환불 계좌와 건강 정보다. 이 데이터를 읽기 전용 mock API 6개와 OpenAPI 스펙으로 감쌌다.
과제 20개는 정답에 필요한 개인정보를 미리 정했다(평균 0.6개, 11개 과제는 0개). 이것이 이상적 최소 노출 기준선이다.

**조건.** Code Mode는 `search`와 `execute` 두 도구를 주고 코드를 `node:vm`에서 실행했다. 2×2로 (a) 시스템 지시에
"필요한 필드만 출력·반환하라"를 더하는 최소 반환 지시, (b) `execute` 설명과 스펙에 응답 타입을 넣는 스키마 제공을 조작했다.
참고용으로 응답 전체를 돌려주는 일반 MCP와 `fields` 인자가 있는 필드 선택 MCP를 같은 API 위에 두었다.

**후속 조건: 구조 보기(peek).** 스키마는 구조와 함께 필드 설명과 값 목록까지 주므로, 어느 부분이 효과를 냈는지 떼어 보려고
이 연구에서 `api.peek(path, query)`이라는 함수를 따로 만들었다. Code Mode의 표준 기능은 아니다. 샌드박스 안에서 `api.get`과 같은 API를 부르되
값을 지우고 키 이름과 타입만 돌려준다. 예를 들어 고객 한 명이면 `{ name: "김민준", phone: "010-…", order: { status: "delivered" } }` 대신
`{ name: "string", phone: "string", order: { status: "string" } }`를 받는다. 목록은 원소 하나의 모양으로 접고, 갈리는 타입은 `"string | null"`처럼 합친다.
peek 결과에 개인정보 값이 하나도 없음은 테스트로 확인했다. peek 조건은 기본 조건에 이 함수와 "값을 빼고 구조만 돌려준다"는 설명 한 줄만 더했고,
사용을 권하거나 개인정보를 언급하지 않았다. 스키마와의 차이는 두 가지다. 스키마는 구조 외에 필드 설명과 값 목록을 주고, **처음부터** 도구 설명에 들어 있다.
peek은 구조만 주고, 에이전트가 **필요할 때 직접 불러야** 한다.

**후속 조건: 구조 미리 주기(types).** peek과 스키마는 주는 내용과 주는 때가 함께 다르므로, 둘을 가르려고 조건을 하나 더 두었다.
peek이 돌려주는 것과 글자 단위로 같은 구조(같은 함수로 만든다)를 처음부터 `execute` 설명에 넣는다. 내용은 peek과 같고 주는 때는 스키마와 같다.

**실행과 채점.** GPT-OSS 120B와 Claude Haiku 5.5를 OpenRouter로 부르고, 모델 2개 × 조건 6개 × 과제 20개 × 3회 = 720회를 돌렸다(비용 $0.39, 시범 실행 $0.01 별도). 후속 조건 두 개를 120회씩($0.15) 더해 모두 960회, $0.55다.
API가 빈 응답을 돌려준 1회(구조 미리 주기)는 모델 행동이 아니라서 실행기가 다시 시도하도록 고친 뒤 그 1회만 다시 돌렸다. 턴 한도(12턴)에 걸린 2회(본 실행 1회, 후속 1회, 모두 GPT-OSS)는 실패로 세되 노출은 집계에 넣었다.
채점기는 노출된 텍스트에서 라벨 값을 찾되 형식 변화(하이픈 유무, 대소문자, 날짜 표기)를 허용하고, 일부만 나온 값은 세지 않는다.
본 실행에서 조건·모델·상황이 섞이게 고른 8회를 직접 검토해, 노출 조각과 채점 표시를 하나씩 대조했다.
후속 두 조건의 기록은 같은 채점기로 셌고, 집계와 에이전트 코드만 확인했다.
잘못 세거나 놓친 값은 없었지만 메일 본문 속 건강 정보(천식, 휠체어)가 민감으로 세어지지 않는 라벨 빈틈을 찾아 고치고 전체를 다시 채점했다.
이 수정으로 기본 조건의 불필요 노출과 민감 노출이 과제당 0.3개씩 늘었고 결론은 바뀌지 않았다.
과제별 필요 목록은 모범 답안이 정답 판정을 통과하고 정확히 그 값만 담는지 테스트로 검증했다.

## 3. 결과

![조건별 불필요 노출](../results/figures/unnecessary-by-condition.svg)

**RQ1. 기본 Code Mode는 일반 MCP만큼 노출했다.** 과제당 불필요 노출은 GPT-OSS 20.6개, Haiku 18.7개로
일반 MCP(19.3개, 21.4개)와 구간이 겹친다. 필요량(0.6개)의 30배가 넘고, 노출의 97%가 불필요했다. 민감 정보도 과제당 3.8-4.1개였다.
샌드박스가 받은 개인정보 중 81-89%가 그대로 모델에게 넘어갔다. 개인정보가 하나도 필요 없는 집계 과제(예: 포인트 최다 고객의 ID)에서
고객 10명 전체(64개)를 돌려주고 모델이 직접 고르는 경우가 가장 컸다.

**RQ2. 에러로는 새지 않았고, 새는 단계는 모델마다 달랐다.** 에러 메시지 경로의 노출은 모든 조건에서 0%였다.
기본 조건에서 GPT-OSS는 불필요 노출의 약 70%가 탐색 단계(console 49%, 중간 return 20%)에서 처음 나왔다. 응답 구조를 모른 채 찍어 보다가 새는 것이다.
Haiku는 71%가 마지막 실행의 return에서 나왔다. 탐색은 적었지만 목록 전체를 넘기고 거르기를 모델에게 맡겼다.
"주된 경로는 탐색 출력"이라는 사전 예상은 한 모델에서만 맞았다.

![경로별 비율](../results/figures/unnecessary-by-channel.svg)

**RQ3. 스키마는 일관되게, 지시는 모델에 따라 효과가 있었다.** 과제당 불필요 노출(기본 → 지시 / 스키마 / 둘 다):

| 모델 | 기본 | 최소 반환 지시 | 스키마 제공 | 둘 다 | 성공률 (기본 → 지시) |
| --- | --- | --- | --- | --- | --- |
| GPT-OSS 120B | 20.6 | 16.6 | 1.4 | 0.1 | 98% → 87% |
| Claude Haiku 5.5 | 18.7 | 0.2 | 1.5 | 0.3 | 100% → 100% |

스키마는 두 모델 모두 노출을 92-93% 줄였고 성공률을 떨어뜨리지 않았다. 접근량은 오히려 늘었는데 노출만 줄었다.
구조를 알면 찍어 볼 이유가 사라진다는 해석과 맞는다. 아래 후속 실험에서 이 해석은 구조를 처음부터 줄 때에 한해 맞았다. 지시는 Haiku에서 99% 감소였지만 GPT-OSS에서는 19%에 그쳤다.
GPT-OSS는 지시가 있어도 집계 과제(T08, T09, T12)에서 고객·연락처 전체를 반환했고, 전화번호 과제에서 "개인정보라 제공할 수 없다"며 답을 거부했다(T06, 3회 중 2회).
두 처치를 함께 주면 두 모델 모두 99% 줄었다.

**후속. 같은 구조라도 언제 주느냐가 갈랐다.** 두 후속 조건을 두 모델에 60회씩 돌렸다. 과제당 불필요 노출(과제 종류별):

| 모델 | 과제 종류 | 기본 | 구조 보기 (peek) | 구조 미리 주기 (types) | 스키마 | peek을 쓴 실행 |
| --- | --- | --- | --- | --- | --- | --- |
| GPT-OSS 120B | 목록·집계 (12개) | 30.1 | 16.4 | 4.6 | 1.4 | 50% |
| GPT-OSS 120B | 단건 조회 (8개) | 6.2 | 4.8 | 3.2 | 1.4 | 13% |
| Claude Haiku 5.5 | 목록·집계 (12개) | 27.8 | 13.0 | 3.9 | 2.1 | 25% |
| Claude Haiku 5.5 | 단건 조회 (8개) | 5.0 | 5.0 | 1.2 | 0.6 | 0% |

먼저 peek 조건은 전체로 20.6 → 11.8, 18.7 → 9.8로 절반 정도 줄었지만 스키마(1.4, 1.5)에는 못 미쳤다. 에이전트가 peek을 쓴 실행은 GPT-OSS 35%, Haiku 15%였다.
과제 종류로 나누면 원인이 갈린다. 목록·집계 과제에서는 peek이 노출을 46-53% 줄였다. 예를 들어 Haiku는 포인트 최다 고객 과제에서
peek으로 모양을 본 뒤 ID만 돌려줘 3회 모두 노출 0이었다(기본 조건 64개). 구조를 몰라서 새는 경로는 이 부분에서 확인된다.
반면 ID로 레코드 하나를 묻는 단건 조회 과제에서는 효과가 작거나 없었다. Haiku는 peek을 한 번도 쓰지 않고 레코드를 통째로 찍어 읽었고,
GPT-OSS는 peek으로 구조를 본 바로 다음 호출에서 레코드 전체를 반환하기도 했다. 노출에는 구조를 몰라서 생기는 것과
레코드를 출력해 읽는 습관에서 생기는 것이 섞여 있다.
같은 구조를 처음부터 넣어 둔 types 조건은 전체로 20.6 → 4.0, 18.7 → 2.8(81%, 85% 감소)이었다. 기본에서 스키마까지 줄어든 폭의 86%, 92%다.
목록·집계는 85-86%, peek이 거의 듣지 않던 단건 조회도 49-77% 줄었고, 탐색 출력(console)으로 샌 값은 하나도 없었다.
성공률은 Haiku 100%, GPT-OSS 95%였다.
즉 스키마 효과의 대부분은 구조를 **처음부터** 주는 데서 온다. 남은 차이는 값 목록과 필드 설명의 몫으로 보인다.
예를 들어 GPT-OSS는 types 조건에서 메일 분류 값이 "refund"라는 것을 몰라 제목에서 영어 단어를 찾다 실패하고,
메일과 고객 표본을 통째로 돌려줬다(71개). 스키마는 `label`의 값 목록을 알려 줘 이런 헤맴이 없었다.

## 4. 논의와 한계

샌드박스의 경계 자체는 쓸모가 있다. 스키마 조건에서 접근 대비 노출은 7-8%까지 떨어졌다. 문제는 경계가 아니라 경계를 넘는 출력을 누가 정하느냐다.
필드 선택 MCP(3.4개, 2.5개)와 비교하면 Code Mode만의 여지도 보인다. 필드 선택은 열을 줄여도 레코드를 거르지 못해,
"11월 생일 고객 수" 같은 집계 과제에서 10개, 20개를 넘겼다. 스키마를 준 Code Mode는 집계를 샌드박스 안에서 끝내 0개, 2개였다.
다만 과제 몇 개에서 보인 경향이라 따로 검증이 필요하다.

이 결과는 세 가지 설계 권고로 이어진다. (1) Code Mode의 프라이버시 이점을 기본값으로 가정하지 말 것,
(2) 완화는 모델마다 효과가 갈리는 지시보다 응답 타입 같은 도구 설계에 두고, 구조 정보는 꺼내 보게 하기보다 처음부터 도구 설명에 넣고, 가능하면 값 목록까지 줄 것, (3) 감시나 필터는 `console`과 `return` 두 출구에 집중할 것.
에러 경로는 이 환경에서 노출이 없었지만, 오류 메시지에 입력을 되돌려 주는 API라면 달라질 수 있다.

한계는 다음과 같다. mock 데이터 30개, 과제 20개, 모델 2개의 파일럿이다. 과제 20개 중 11개는 답에 개인정보가 필요 없어,
과제 구성이 달라지면 평균 노출량도 달라진다. 스키마 효과는 응답 구조가 전혀 없는 스펙과의 비교라
이미 스키마가 있는 환경에서는 개선 폭이 작을 수 있다. 노출은 문자열 일치로 세므로 요약·바꿔 말하기는 놓친다(과소 추정 쪽).
실행기는 단순한 도구 호출 루프로, 출력 길이 제한이나 자체 지시를 가진 실제 제품과 조건이 다르다.
peek과 types는 이 연구에서 만든 한 가지 구현이고, peek 사용률(15-35%)은 도구 설명 문구에 따라 달라질 수 있다.
또한 모델이 최종 답변으로 사용자에게 보여 준 것은 재지 않았다. "골드 고객이 몇 명인가"에 세 사람의 이름까지 답한 경우처럼,
모델을 거친 개인정보가 사용자 화면으로 다시 나가는 경로는 이 연구의 범위 밖이다.

## 5. 후속 연구

- **사용자 인식:** 사용자는 샌드박스 출력을 보지 못한다. 모델에게 넘어간 값을 보여 주는 인터페이스가 위임 범위와 신뢰 판단을 바꾸는지 사용자 연구로 확인한다.
- **값 목록과 필드 설명:** 구조 미리 주기(types)와 스키마 사이에 남은 차이를 값 목록(enum)과 필드 설명으로 나눠 본다.
- **출구 필터:** `console`·`return`에서 과제와 무관한 라벨 값을 가리는 필터의 노출·성공률 교환을 잰다.
- **규모와 모델:** 레코드 수, 응답 크기, 모델 수를 늘려 이 파일럿의 비율이 유지되는지 본다.
