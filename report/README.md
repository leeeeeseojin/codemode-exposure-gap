# 샌드박스의 약속과 에이전트의 출력: Code Mode 개인정보 노출 파일럿

## 1. 동기

Code Mode는 에이전트가 API를 부르는 코드를 짜서 샌드박스에서 실행하게 한다. 도구 결과가 모델 컨텍스트를 거치지 않으므로
"중간 데이터는 샌드박스에 머문다"는 프라이버시 이점이 함께 소개된다. 그러나 모델에게 무엇이 넘어갈지는 에이전트가 쓴
`console.log`와 `return`이 정한다. 응답 구조를 확인하려고 레코드를 한 번 찍기만 해도 샌드박스의 경계는 의미를 잃는다.
이 파일럿은 그 약속이 실제 에이전트 행동에서 지켜지는지 처음으로 잰다.

- RQ1. 과제에 필요한 최소한보다 얼마나 많은 개인정보를 모델에게 노출하는가?
- RQ2. 노출은 탐색 출력, 최종 반환값, 에러 메시지 중 어디서 생기는가?
- RQ3. 최소 반환 지시와 스키마 제공은 노출을 얼마나 줄이는가?

## 2. 방법

**접근과 노출.** 샌드박스 코드나 도구 서버가 API에서 받은 개인정보를 *접근*, 실제로 모델 컨텍스트에 들어간 것을 *노출*로 나눠 기록했다.
측정 대상은 노출이고, 단위는 서로 다른 개인정보 값 하나다.

**환경.** 가짜 고객 10명, 거래처 연락처 10명, 고객센터 메일 10통을 만들고 필드마다 개인정보·민감 정보 라벨을 붙였다.
민감 정보는 카드 번호, 건강 메모, 여권 번호, 메일 본문 속 환불 계좌다. 이 데이터를 읽기 전용 mock API 6개와 OpenAPI 스펙으로 감쌌다.
과제 20개는 정답에 필요한 개인정보를 미리 정했다(평균 0.6개, 11개 과제는 0개). 이것이 이상적 최소 노출 기준선이다.

**조건.** Code Mode는 `search`와 `execute` 두 도구를 주고 코드를 `node:vm`에서 실행했다. 2×2로 (a) 시스템 지시에
"필요한 필드만 출력·반환하라"를 더하는 최소 반환 지시, (b) `execute` 설명과 스펙에 응답 타입을 넣는 스키마 제공을 조작했다.
참고용으로 응답 전체를 돌려주는 일반 MCP와 `fields` 인자가 있는 필드 선택 MCP를 같은 API 위에 두었다.

**실행과 채점.** GPT-OSS 120B와 Claude Haiku 5.5를 OpenRouter로 부르고, 조건 6개 × 과제 20개 × 3회 = 720회를 돌렸다(비용 $0.39).
채점기는 노출된 텍스트에서 라벨 값을 찾되 형식 변화(하이픈 유무, 대소문자, 날짜 표기)를 허용하고, 일부만 나온 값은 세지 않는다.
시범 실행 18회를 사람이 직접 검토해 채점 오류가 없음을 확인했고, 모범 답안 테스트로 과제별 필요 목록을 검증했다.

## 3. 결과

![조건별 불필요 노출](../results/figures/unnecessary-by-condition.svg)

**RQ1. 기본 Code Mode는 일반 MCP만큼 노출했다.** 과제당 불필요 노출은 GPT-OSS 20.2개, Haiku 18.4개로
일반 MCP(19.1개, 21.1개)와 구간이 겹친다. 필요량(0.6개)의 30배가 넘고, 노출의 97%가 불필요했다. 민감 정보도 과제당 3.5~3.8개였다.
샌드박스가 받은 개인정보 중 81~89%가 그대로 모델에게 넘어갔다. 개인정보가 하나도 필요 없는 집계 과제(예: 포인트 최다 고객의 ID)에서
고객 10명 전체(64개)를 돌려주고 모델이 직접 고르는 경우가 가장 컸다.

**RQ2. 에러로는 새지 않았고, 새는 단계는 모델마다 달랐다.** 에러 메시지 경로의 노출은 모든 조건에서 0%였다.
기본 조건에서 GPT-OSS는 불필요 노출의 70%가 탐색 단계(console 49%, 중간 return 20%)에서 처음 나왔다. 응답 구조를 모른 채 찍어 보다가 새는 것이다.
Haiku는 71%가 마지막 실행의 return에서 나왔다. 탐색은 적었지만 목록 전체를 넘기고 거르기를 모델에게 맡겼다.
"주된 경로는 탐색 출력"이라는 사전 예상은 한 모델에서만 맞았다.

![경로별 비율](../results/figures/unnecessary-by-channel.svg)

**RQ3. 스키마는 일관되게, 지시는 모델에 따라 효과가 있었다.** 과제당 불필요 노출(기본 → 지시 / 스키마 / 둘 다):

| 모델 | 기본 | 최소 반환 지시 | 스키마 제공 | 둘 다 | 성공률 (기본 → 지시) |
| --- | --- | --- | --- | --- | --- |
| GPT-OSS 120B | 20.2 | 16.4 | 1.4 | 0.1 | 98% → 87% |
| Claude Haiku 5.5 | 18.4 | 0.2 | 1.5 | 0.3 | 100% → 100% |

스키마는 두 모델 모두 노출을 92~93% 줄였고 성공률을 떨어뜨리지 않았다. 접근량은 오히려 늘었는데 노출만 줄었다.
구조를 알면 찍어 볼 이유가 사라진다는 해석과 맞는다. 지시는 Haiku에서 99% 감소였지만 GPT-OSS에서는 19%에 그쳤다.
GPT-OSS는 지시를 따르려다 구조를 몰라 헤맨 끝에 전체를 반환했고(T04), 전화번호 과제에서 "개인정보라 제공할 수 없다"며 답을 거부했다(T06, 3회 중 2회).
두 처치를 함께 주면 두 모델 모두 99% 줄었다.

## 4. 논의와 한계

샌드박스의 경계 자체는 쓸모가 있다. 스키마 조건에서 접근 대비 노출은 7~8%까지 떨어졌다. 문제는 경계가 아니라 경계를 넘는 출력을 누가 정하느냐다.
이 결과는 세 가지 설계 권고로 이어진다. (1) Code Mode의 프라이버시 이점을 기본값으로 가정하지 말 것,
(2) 완화는 모델마다 효과가 갈리는 지시보다 응답 타입 같은 도구 설계에 둘 것, (3) 감시나 필터는 `console`과 `return` 두 출구에 집중할 것.

한계는 다음과 같다. mock 데이터 30개, 과제 20개, 모델 2개의 파일럿이다. 스키마 효과는 응답 구조가 전혀 없는 스펙과의 비교라
이미 스키마가 있는 환경에서는 개선 폭이 작을 수 있다. 노출은 문자열 일치로 세므로 요약·바꿔 말하기는 놓친다(과소 추정 쪽).
실행기는 단순한 도구 호출 루프로, 출력 길이 제한이나 자체 지시를 가진 실제 제품과 조건이 다르다.

## 5. 후속 연구

- **사용자 인식:** 사용자는 샌드박스 출력을 보지 못한다. 모델에게 넘어간 값을 보여 주는 인터페이스가 위임 범위와 신뢰 판단을 바꾸는지 사용자 연구로 확인한다.
- **출구 필터:** `console`·`return`에서 과제와 무관한 라벨 값을 가리는 필터의 노출·성공률 교환을 잰다.
- **규모와 모델:** 레코드 수, 응답 크기, 모델 수를 늘려 이 파일럿의 비율이 유지되는지 본다.
